# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Aaron's personal Neovim configuration. It is intentionally minimal but does use **lazy.nvim** as a plugin manager ([lua/config/lazy.lua](lua/config/lazy.lua)), which auto-loads every spec under `lua/plugins/*.lua`. Currently installed plugins: **snacks.nvim** (dashboard + picker + file explorer + LSP-aware file rename/delete, [lua/plugins/snacks.lua](lua/plugins/snacks.lua)), **vim-table-mode** ([lua/plugins/table-mode.lua](lua/plugins/table-mode.lua)), **mini.move** (move lines/selections, [lua/plugins/mini-move.lua](lua/plugins/mini-move.lua)), **autolist.nvim** (list continuation/renumbering, [lua/plugins/autolist.lua](lua/plugins/autolist.lua)), **mini.surround** (add/delete/replace surrounding pairs, [lua/plugins/mini-surround.lua](lua/plugins/mini-surround.lua)), and **mini.ai** (extended around/inner text objects, [lua/plugins/mini-ai.lua](lua/plugins/mini-ai.lua)) — added solely to override its built-in `s` (sentence) object with a newline-aware version ([lua/config/AG-newline-sentence-textobject.lua](lua/config/AG-newline-sentence-textobject.lua)) so `is`/`as` never cross a line boundary. Don't assume any plugin beyond these six is present, and check the actual files under `lua/plugins/` rather than trusting this list if it's been a while — it drifts. The editor's primary use case here is prose/Markdown/JSON editing; general code editing is handled in VS Code and Xcode, which shapes several of the design decisions below (e.g. display-line-based navigation).

**File management** (rename/delete) goes through snacks.nvim, not vim-eunuch (removed 2026-08-11): vim-eunuch's `:Rename`/`:Move` didn't notify LSP clients of the file move, so any attached LSP server's tracked references/imports silently went stale. `Snacks.rename.rename_file()` (bound to `<Leader>fR`) fires `workspace/willRenameFiles`/`didRenameFiles` before moving the file. `<Leader>fD` deletes the current buffer's file (permanent, not trash) and closes the buffer — same effect as vim-eunuch's `:Delete`. Both keymaps live in [lua/plugins/snacks.lua](lua/plugins/snacks.lua). The file explorer (`<Leader>fe`) also has `r`/`d`/`c`/`m` bound to the same rename/delete plus copy/move, for when you're browsing rather than acting on the current buffer. Lost from vim-eunuch and not replaced: `:Mkdir`, `:Chmod`, `:SudoWrite`/`:SudoEdit`, `:Cfind`/`:Clocate`/`:Lfind`/`:Llocate`, `:Wall`.

## Structure

```
~/.config/nvim/
├── init.lua                                        -- entry point: sets leader, loads lazy.nvim, colorscheme, clipboard, wrap toggle, reload keymap
└── lua/
    ├── config/
    │   ├── lazy.lua                                 -- bootstraps lazy.nvim, imports lua/plugins/*.lua
    │   ├── AG-display-line-based-navigation.lua      -- display-line navigation/operator remaps + custom `dr` operator
    │   ├── AG-titlecase.lua                          -- title case function (`gl`)
    │   ├── AG-table-augmentation.lua                 -- vim-table-mode augmentations (Tab/S-Tab cell nav)
    │   ├── AG-autosave.lua                         -- persistent undo, backups, autosave, auto-persist new buffers
    │   ├── AG-atext-guard.lua                        -- disable/enable aText around Insert mode to prevent buffer corruption
    │   ├── AG-newline-sentence-textobject.lua        -- mini.ai custom `s` object: newline is always a sentence boundary
    │   └── autocmds.lua                              -- autocommands (e.g. auto-`lcd` to current file's directory)
    └── plugins/
        ├── snacks.lua                                -- folke/snacks.nvim spec (dashboard + picker)
        ├── table-mode.lua                            -- dhruvasagar/vim-table-mode spec
        ├── mini-move.lua                             -- echasnovski/mini.move spec (move lines/selections)
        ├── autolist.lua                              -- gaoDean/autolist.nvim spec (list continuation/renumbering)
        ├── mini-surround.lua                         -- echasnovski/mini.surround spec (surrounding pairs)
        └── mini-ai.lua                                -- echasnovski/mini.ai spec (text objects; custom sentence object)
```

`init.lua` requires `config.lazy` first (which loads plugins), then the `config.AG-*`/`config.autocmds` modules. Any new non-plugin modules should go under `lua/config/` and be `require()`'d from `init.lua`, following this same convention; new plugins get their own spec file under `lua/plugins/`, named after the plugin.

## Testing changes

There is no build/lint/test tooling. To validate a change:
- Reload the running config with `<Leader>rc` (sources `$MYVIMRC` and prints "Config reloaded!"), or restart Neovim. `<Leader>rc` first clears every `package.loaded` entry under the `config.` namespace, so it actually re-reads edited files under `lua/config/` from disk rather than re-running Lua's cached (stale) copies — this is automatic for any file added there, nothing to update when adding new modules. It does *not* cover `lua/plugins/*.lua`; those are lazy.nvim-managed and need `:Lazy reload` instead.
- Sanity-check syntax by loading the file headlessly, e.g.:
  ```sh
  nvim --headless -u init.lua +qa
  ```

## Target environments

This config must work identically in **two** Neovim runtimes:
1. **VimR** (macOS GUI wrapper with a bundled/embedded Neovim runtime).
2. **Neovim in iTerm2** (standard terminal Neovim via Homebrew) — treat this as the reference/"correct" baseline when behavior diverges between the two.

`init.lua` contains a workaround (must stay as the first executable lines, before any `require()`) for a VimR-specific bug where its embedded runtime doesn't reliably populate `package.path` from `stdpath('config')`. This does not affect terminal Neovim but is harmless/idempotent there, so don't remove it. Resolved — no further action needed on this.

This directory is also expected to be portable across machines (managed via GNU Stow in a separate dotfiles repo), so avoid hardcoding machine-specific absolute paths.

## Key design decisions (lua/config/AG-display-line-based-navigation.lua)

- **`j`/`k`/`0`/`$` are swapped with `gj`/`gk`/`g0`/`g$`** so that normal/visual/operator-pending motions operate on *display* (visual screen) rows instead of *logical* buffer lines — important for wrapped prose where one logical line spans many screen rows. `gj`/`gk`/`g0`/`g$` are preserved as the escape hatch to original logical-line behavior. All four remaps are applied to `n`, `v`, *and* `o` modes together — operator-pending inclusion is deliberate: without it, `d$` on a wrapped line would delete to the end of the whole logical line/paragraph rather than just the visible row, defeating the point of the remap. When editing these, keep all three modes in sync.
- **`dr` ("delete row")** is a custom function (not a remap of `dd`) that deletes only the current display row. `dd` can't be redefined for this because it's a linewise operator baked into core Vim with no concept of an addressable "display row" — hence a standalone function bound to a new key, leaving `dd`/macros/plugins that assume linewise semantics unaffected. Its register behavior deliberately mirrors a native characterwise delete: writes `"` (unnamed) and `"-` (small-delete register), but does **not** write `"1`-`"9` (reserved for linewise deletes). Known gaps, not yet implemented: no dot-repeat (`.`) support (would need `vim.o.operatorfunc` or vim-repeat), and no count support (`3dr` is ignored).
- **Insert-mode `<D-c>` is mapped to `<Nop>`**: Superwhisper's "Super" mode context-awareness feature sends a real Cmd+C (to grab existing/selected text as context) when its ⌥Z hotkey starts recording. Per the Cmd-key discussion above, that reaches terminal Neovim untouched like `<D-Up>`/`<D-Down>`/`<D-'>` do — but with no mapping, it fell through and got typed as the literal characters `<D-c>` instead of being consumed. Confirmed 2026-09-13 not to happen at a bare iTerm2 shell prompt, only inside Neovim Insert mode. No Insert-mode use for Cmd+C otherwise, so it's swallowed outright.

See [docs/display-line-editing.md](docs/display-line-editing.md) for the full narrative history of these decisions and untested follow-up ideas (dot-repeat, count support, cross-environment verification). Note: that doc predates lazy.nvim/snacks.nvim/vim-table-mode being installed, so treat its "no plugin manager"-era statements as historical, not current.

## Key design decisions (lua/config/AG-autosave.lua)

- **Persistent undo + centralized backups**: `undofile`/`undodir` and `backup`/`backupdir` are pointed at `stdpath('state')` (not scattered `~` files next to originals) so undo history survives closing a file and every overwrite keeps a pre-write snapshot. `backupdir` has a trailing `//` so same-named files from different directories don't collide.
- **Autosave of already-named buffers is debounced 5s off `TextChanged`/`TextChangedI`, plus an immediate save on `InsertLeave`/`FocusLost`, not `CursorHold`/`updatetime`**: each edit (re)schedules a `vim.uv` one-shot timer 5s out, and a further edit before it fires cancels and reschedules it, so a save only actually happens once 5s have passed since the *last* edit — nothing runs at all while idle or mid-typing (this replaced an earlier plain-repeating-timer version that polled every 5s regardless of activity; reverted since it was needless overhead here — Aaron's actual typing has frequent natural pauses, so the repeating-timer's original justification, continuous pause-free typing never triggering a save, didn't apply). Deliberately not `CursorHold`/`updatetime`, since `updatetime` is a global option that also controls core swapfile write frequency, and this module has no reason to touch a global for a save interval it alone owns. In practice `InsertLeave` fires very often in normal Vim usage (any `<Esc>`), so most saves happen immediately rather than waiting out the debounce — the debounce mostly matters for long uninterrupted stretches spent in Insert mode. Always uses `:update` (no-op if nothing changed). The pending timer handle is stashed on `_G.__ag_autosave_timer` (not a local) so a `<Leader>rc` reload can find and cancel a still-pending timer from the previous module load — libuv timers aren't tied to Lua's `package.loaded` cache, so without this a reload mid-debounce would leak one running independently forever. Verified via headless tests: a second edit measurably resets the 5s window rather than the write firing off the first edit, and `InsertLeave` saves immediately without waiting.
- **Brand-new unnamed buffers are auto-persisted to `~/Library/CloudStorage/OneDrive-UW/ag-buffer/` on first edit**, not throttled — this one-time "give this buffer a real file on disk" action deliberately fires on `TextChanged`/`TextChangedI` immediately (guarded by a buffer-local flag so it only runs once) rather than waiting for a CursorHold pause, since the whole point is protecting content typed just before a crash that happens *during* continuous typing. Filenames are `YYYY-MM-DD_HHMMSS.<ext>` (collision-suffixed `_2`, `_3`, ... for same-second collisions), defaulting to `.md` since filetype is usually still unset for a genuinely new buffer. Applies to all buftypes/filetypes, not just prose — deliberate, since there's no reason to leave a stray code scratch buffer unprotected just because "real" code editing happens elsewhere.
- OneDrive is used as the sync target because it's HIPAA-compliant per Aaron's institution — don't swap in a different cloud provider without checking that constraint still holds.
- **Known quirk, deliberately not worked around**: in VimR (not terminal nvim), a `:w` into `ag-buffer/` shortly after the auto-persist write has occasionally reported success while the file didn't yet exist on disk moments later, with an identical retry then succeeding — looks like a VimR-specific interaction with the macOS FileProvider layer backing the OneDrive mount. A `BufWritePost`-based verify-and-retry safety net was tried (2026-07-08) and reverted at Aaron's request: it added a delayed re-check after every OneDrive write on top of an already-frequent autosave, for a rarely-hit edge case that's easy to sidestep by not immediately re-saving under a new name (or by using "save as" workflows instead). If this resurfaces as a real problem, revisit the reverted approach rather than re-deriving it from scratch.
- **All of this module's autocmds live in a single `AGAutosave` augroup created with `clear = true`**, making `setup()` idempotent no matter how many times it runs (e.g. repeated `<Leader>rc` reloads within one session) — without this, every reload piled up another full copy of every autocmd here.
- **The new-buffer persist autocmd is defined with `nested = true`**: its callback does a `keepalt write`, and without `nested`, Neovim's default no-nested-autocmds behavior means that write's `BufWritePost` wouldn't cascade into the lcd-to-file's-directory autocmd (`autocmds.lua`) — the file would still get written correctly, but the working directory would silently stay wherever nvim was launched from instead of following the new file. Caught 2026-07-08 when a subsequent manual `:w` landed in the launch directory instead of `ag-buffer/`.

## Key design decisions (lua/config/AG-atext-guard.lua)

- **Problem**: aText (system-wide text expansion) watches raw keystrokes at the OS level with no awareness that Vim is modal. When a Normal-mode command like `dw` consumes keystrokes without inserting any text, aText still appends them to its own internal "recently typed" buffer, which then diverges from the actual document content — causing (1) a real abbreviation typed right after a command failing to match, since aText's buffer has phantom command characters glued in front of it, and (2) phantom characters coincidentally combining with subsequently-typed real text to trigger an unrelated, unintended expansion (whose inserted keystrokes then get interpreted as Vim commands if this happens outside Insert mode).
- **Rejected approach**: a synthetic lone Command-key tap via `osascript`/System Events (which resets aText's buffer as a side effect) timed off `InsertEnter`. Rejected because the synthetic key-down's actual OS-level delivery is delayed by `osascript`'s process/interpreter cold-start (~100-300ms), during which a real physical keystroke could coincide with it and get composed into an unintended system shortcut (Cmd+S, Cmd+W, Cmd+Q, etc.) — a risk inherent to injecting a synthetic keyboard event at all, regardless of sync/async timing choices.
- **Actual approach**: aText exposes its own AppleScript `enable`/`disable` commands. Toggling those isn't a synthetic keyboard event, so there's no possibility of colliding with real keystrokes to form an accidental shortcut, and it's fully deterministic — aText observes nothing while disabled, so no partial buffer contamination is possible no matter how many phantom Normal-mode commands run. Aaron confirmed empirically that disabling and re-enabling aText leaves its buffer cleared, not just paused-with-stale-content-intact.
- **`enable` (on `InsertEnter`) is synchronous (`vim.fn.system`); `disable` (on `InsertLeave`) is async (`vim.fn.jobstart`)**: `enable` blocks until aText is confirmed re-enabled, closing the gap where an abbreviation typed immediately after entering Insert mode might not expand. `disable` has no equivalent need to block — any lag just means aText sees a few more trailing Normal-mode phantom keystrokes for a moment longer, which is harmless, since the next real typing session still starts clean regardless (guaranteed by the synchronous enable). Full sync on both ends would add a real, guaranteed pause to every single Insert-mode entry *and* exit — `i`/`a`/`o` and `<Esc>` are some of the most frequent keys in modal editing — so only paying that cost on the one transition that actually needs it keeps the tax to a minimum.
- **Known residual gap, not fully worked around**: even a synchronous `enable` only guarantees ordering with respect to Neovim's own processing — it can't control when the user physically generates the next keystroke. aText watches raw key events at the OS level independent of Neovim's input queue, so if real typing resumes with zero pause immediately after `i`, it's possible to outrun the `enable` call's own latency (process spawn + Apple Event round-trip) and have the first character or two land before aText has actually finished coming back online. Confirmed happening in practice 2026-07-08. Always a silent missed expansion, never corruption — accepted as an inherent limit of a reactively-triggered external process, not a bug to keep chasing.
- **`enable.scpt`/`disable.scpt` are precompiled once (via `osacompile`) into `stdpath('state')/atext-guard/`, guarded by a `filereadable` check, rather than passed as `-e` source text on every call**: skips AppleScript's parse/compile step on every `InsertEnter`/`InsertLeave` (which fire on essentially every mode switch), narrowing (not eliminating) the residual gap above — the remaining, larger cost is `osascript`'s own process/interpreter startup, which precompiling doesn't touch. Compiled `.scpt` files are generated binary artifacts, not source, so they're kept out of the portable Stow-managed config tree — same reasoning as `AG-autosave.lua`'s `undodir`/`backupdir`.
